## Исправления, найденные именно во время сертификации

### 1. Обход DNS-пиннинга платёжными провайдерами

В версии 2.2.0 staging-запросы уже использовали защищённый транспорт, однако обычные методы платёжных провайдеров создавали собственные `httpx.AsyncClient`.

Это позволяло обходить общий механизм DNS-пиннинга.

Исправление: все исходящие запросы YooKassa, Platega и RollyPay теперь используют общий защищённый клиент с:

- проверкой публичного HTTPS URL;
- разрешением DNS непосредственно перед соединением;
- запретом private/local адресов;
- отключёнными перенаправлениями;
- сохранением исходного имени хоста для TLS.

Добавлен регрессионный тест, запрещающий появление прямого `httpx.AsyncClient` в модуле платежей.

### 2. Ошибка release verifier

Старый verifier содержал некорректное использование shell-переменной внутри одинарно заключённой строки Python.

Кроме того, логика была привязана к историческому имени артефакта.

Исправление: verifier теперь:

1. определяет текущий ZIP или принимает `RELEASE_ARTIFACT`;
2. вычисляет имя detached manifest;
3. проверяет цифровую подпись;
4. проверяет соответствие artifact в manifest;
5. вычисляет SHA-256 потоково;
6. сравнивает его с manifest;
7. проверяет целостность ZIP.

### 3. Некорректно объявленная поддержка автопродления

API возвращал пустой `supported_providers`, хотя реализация автопродления присутствует для YooKassa.

Теперь API явно сообщает только реально реализованный провайдер: `yookassa`.

## Frontend

Исходники Admin и Mini App проверены статически.

В текущей изолированной среде отсутствует гарантированно доступный npm registry, поэтому полноценная установка зависимостей и production-сборка frontend не засчитаны как выполненные.

Проект содержит соответствующие команды сборки, а установщик генерирует lock-файлы и использует `npm ci`.

## Что невозможно подтвердить без внешней инфраструктуры

Не выдаётся за PASS то, что требует реального окружения:

- реальные sandbox-платежи;
- реальный Remnawave API;
- полный Docker runtime;
- Trivy;
- Syft/SBOM;
- pip-audit;
- внешний npm registry;
- нагрузочный тест реального VPS;
- фактическое переключение production traffic;
- восстановление из реального удалённого S3 backup.

Это ограничения среды проверки, а не скрытые PASS.

## Рекомендованный production gate

Перед включением реальных платежей выполнить:

1. `./scripts/integration-test.sh`;
2. `./scripts/staging-e2e.sh`;
3. `./scripts/security-scan.sh`;
4. production-like `docker compose` запуск;
5. sandbox payment flow для каждого подключённого провайдера;
6. backup → destroy → restore тест;
7. canary deployment с наблюдением error rate и latency;
8. финальную проверку detached manifest и подписи.
